## 7. Artwork production

All artwork is produced at high resolution, reviewed in context, and exported into responsive web formats. For every final illustration slot, create at least three candidates before selecting and retouching a final.

Required families:

- Homepage workshop atmosphere and atlas transition.
- Three product-world candidates for each of four featured projects.
- Three process/outcome candidates for each of four case studies.
- Three roadmap transition candidates.
- Three social-card compositions.
- Three favicon/wordmark-support treatments where needed; real product logos are not AI-regenerated.

Production rules:

- Generated art contains no application UI, fake statistics, customer data, or claimed evidence.
- Original screenshots and logos are layered separately in the webpage.
- Keep layered working files, prompts, rejected directions, dates, and manual edit notes as provenance evidence.
- Kirsten materially directs, selects, composites, retouches, typesets, and approves final art.
- Export master raster art at up to 3840×2160 or 2160×3840 where the composition requires it, then create AVIF/WebP derivatives with PNG/JPEG fallbacks only where necessary.
- Add meaningful alt text for informational art and empty alt text for purely decorative terrain.

## 8. Screenshot integrity contract

- Read source dimensions at build time.
- Generate width and height attributes from source metadata.
- Preserve source aspect ratio in every breakpoint.
- Use contain-fit; never crop into application UI.
- Never apply perspective transforms to evidence images.
- Never run real screenshots through image generation.
- Never place generated mock data into screenshots and describe it as real application evidence.
- When fresh screenshots are required, run the actual app using isolated synthetic data, verify there are no visible errors, and capture the complete compact window.
- Synthetic data uses fictional names, `example.invalid` email addresses, reserved/example phone values, and no client or personal information.

## 9. Experience and motion

- Static HTML provides the complete reading and navigation experience.
- The atlas uses high-resolution authored artwork and semantic HTML. Three.js/WebGL patterns inform depth and motion direction, but no heavy decorative 3D runtime ships unless it later proves a measurable interaction benefit.
- Stable WebGL is the default. WebGPU/TSL may appear only as a capability-gated experiment after the WebGL path is complete.
- Native scroll controls the narrative; no scroll-jacking.
- Pause animation when the canvas is offscreen or the tab is hidden.
- Cap device pixel ratio, use compressed geometry/textures, and keep a static poster fallback.
- Reduced-motion visitors receive the final readable state without scroll-linked movement.
- Keyboard focus or project selection produces the same informational state as pointer interaction.

## 15. Repository and loss-prevention strategy

The current repository `YazeKT/yazekt.github.io` remains private until the publication gate.

Before making anything public:

- Secret-scan the entire history and final artifact.
- Inspect tracked files, large files, `.env`, databases, exports, test profiles, browser data, local paths, and client information.
- Preserve an encrypted off-platform Git bundle backup and a separate copy of original layered artwork.
- Require passkey or hardware-backed 2FA, store recovery codes offline, maintain two verified account emails, and review authorized apps, tokens, deploy keys, collaborators, and webhooks.
- Sign release tags and publish checksums for release artifacts.

Publication architecture is a final explicit choice:

1. **Public source repository:** change `YazeKT/yazekt.github.io` to public and accept that GitHub users may view and fork it. Apply proprietary notices and the strongest available ruleset.
2. **Private authoring plus public output repository:** retain the editable Astro source privately, publish only generated static output in the public `YazeKT/yazekt.github.io` repository, and deploy through an owner-controlled release step. This hides authoring files but cannot stop downloading the deployed site.
3. **Private source and GitHub Pages with a paid plan:** keep the repository private and use GitHub Pages if the account plan supports it; the website itself remains public.

Recommended for Kirsten's stated protection goal: **private authoring plus public output repository**, unless she explicitly prefers public source for recruiter inspection.
